# Отчет по реализации модуля "Учет финансов"

## Обзор решения

Реализована система учета финансов для ВШЭ-Банка с следующим функционалом:

### Основной функционал:
- Управление банковскими счетами (создание, редактирование баланса)
- Управление категориями операций (доходы/расходы)
- Учет финансовых операций с привязкой к счетам и категориям

### Дополнительный функционал:
- Аналитика: расчет разницы доходов и расходов за период
- Группировка операций по категориям
- Экспорт данных в JSON формат
- Автоматический пересчет балансов
- Измерение времени выполнения пользовательских сценариев

## Реализованные принципы SOLID

### 1. Single Responsibility Principle (SRP)
- `BankAccountService` - отвечает только за управление счетами
- `OperationService` - отвечает только за управление операциями  
- `CategoryService` - отвечает только за управление категориями
- `AnalyticsService` - отвечает только за аналитические вычисления

### 2. Open/Closed Principle (OCP)
- `ExportVisitor` интерфейс позволяет добавлять новые форматы экспорта без изменения существующего кода
- `ValidationStrategy` интерфейс позволяет добавлять новые правила валидации
- `Command` интерфейс позволяет добавлять новые пользовательские сценарии

### 3. Liskov Substitution Principle (LSP)
- Все реализации `ExportVisitor` могут использоваться взаимозаменяемо
- Все реализации `ValidationStrategy` следуют единому контракту
- Все декораторы команд совместимы с базовым интерфейсом `Command`

### 4. Interface Segregation Principle (ISP)
- Интерфейсы разделены по функциональности: `Command`, `ExportVisitor`, `ValidationStrategy`
- Клиенты зависят только от необходимых им интерфейсов

### 5. Dependency Inversion Principle (DIP)
- Высокоуровневые модули зависят от абстракций, а не от деталей
- `Facade` зависит от интерфейсов сервисов, а не от их реализаций
- Сервисы инъектируются через конструкторы
- `DIContainer` управляет зависимостями

## Реализованные принципы GRASP

### High Cohesion
- `BankAccountService` содержит только методы для работы со счетами
- `AnalyticsService` содержит только аналитические методы
- `OperationBuilder` отвечает только за построение операций
- Каждый экспортер отвечает только за свой формат

### Low Coupling
- `Facade` уменьшает связность между клиентом и сервисами
- Сервисы общаются через четко определенные интерфейсы
- Команды инкапсулируют зависимости
- Посетитель отделяет алгоритм экспорта от структуры данных

## Реализованные паттерны GoF

### 1. Фасад (Facade)
- **Класс:** `Facade`
- **Важность:** Упрощает взаимодействие с комплексной системой сервисов, предоставляя единый упрощенный интерфейс
- **Обоснование:** Скрывает сложность работы с множеством сервисов от клиентского кода

### 2. Команда (Command)
- **Классы:** `Command`, `AccountCommand`, `OperationCommand`
- **Важность:** Инкапсулирует запросы как объекты, позволяя параметризовать клиентов с различными запросами
- **Обоснование:** Позволяет легко добавлять новые пользовательские сценарии и поддерживать отмену операций

### 3. Декоратор (Decorator)
- **Класс:** `CommandDecorator`
- **Важность:** Динамически добавляет новую функциональность объектам
- **Обоснование:** Позволяет добавлять измерение времени к любым командам без изменения их исходного кода

### 4. Шаблонный метод (Template Method)
- **Класс:** `DataImporter`
- **Важность:** Определяет скелет алгоритма, позволяя подклассам переопределять определенные шаги
- **Обоснование:** Устраняет дублирование кода в различных импортерах, оставляя только различия в парсинге

### 5. Посетитель (Visitor)
- **Классы:** `ExportVisitor`, `JsonExport`
- **Важность:** Позволяет добавлять новые операции к объектам без изменения их классов
- **Обоснование:** Отделяет алгоритм экспорта от структуры доменных объектов, упрощая добавление новых форматов

### 6. Фабрика (Factory)
- **Класс:** `Factory`
- **Важность:** Инкапсулирует логику создания объектов
- **Обоснование:** Централизует создание доменных объектов и обеспечивает их валидацию при создании

### 7. Строитель (Builder)
- **Класс:** `OperationBuilder`
- **Важность:** Пошаговое создание сложных объектов
- **Обоснование:** Упрощает создание объектов Operation с множеством параметров, делая код более читаемым

### 8. Стратегия (Strategy)
- **Классы:** `ValidationStrategy`, `AmountValidationStrategy`, `CategoryValidationStrategy`
- **Важность:** Определяет семейство алгоритмов, инкапсулирует каждый из них и делает их взаимозаменяемыми
- **Обоснование:** Позволяет легко добавлять новые правила валидации без изменения существующего кода

### Инструкция по запуску

1. Клонируйте репозиторий
2. Перейдите в директорию проекта
3. Запустите приложение:
```
chmod +x gradlew
./gradlew build #сборка и запуск тестов
java -cp build/classes/java/main hw2.Main #запуск консольного приложения
```
